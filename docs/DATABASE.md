# Database

Neon PostgreSQL, in its own `cloakpay` database inside the existing Neon project.
The application connects with `DATABASE_URL`; `scripts/db-bootstrap.mjs` uses
`DATABASE_ADMIN_URL` once, to create the database itself.

## Migrations

Migrations are plain SQL files in `db/migrations/`, applied in filename order.
The runner records what it has applied and refuses to run a file twice.

```bash
npm run db:migrate          # apply anything pending
npm run db:status           # show what is applied
```

| File | Contents |
| --- | --- |
| `001_init.sql` | users, oauth_identities, sessions, oauth_states, wallets, shielded_notes, payment_links, payment_requests, payments, pool_events, notifications, audit_events, rate_limits |
| `002_identity_and_notes.sql` | viewing keys on wallets, link claim columns, pool_state, the one-claim-per-link guard |

Migrations are additive and idempotent (`create table if not exists`,
`add column if not exists`) so re-running them against an existing database is
safe. Anything destructive would be a new file with an explicit down path, and
there is none yet.

## Conventions

- `snake_case`, singular table names.
- Every id is a UUID generated by the database.
- Every timestamp is `timestamptz` in UTC.
- Money is `numeric(78,0)`, integer wei. Never a float, never a string of
  digits that a JSON parser might turn into a float.
- Uniqueness that matters is a database constraint, not an application check.

## Tables that carry the security properties

**`users.username_lower`** is a generated column with a unique index, so username
uniqueness is case-insensitive and enforced by Postgres, not by a race-prone
`SELECT` in an API route.

**`oauth_identities`** is unique on `(provider, provider_account_id)`. That pair
is the account's real identity; `handle` and `email` are display metadata that may
change or be reassigned.

**`sessions.token_hash`** stores a SHA-256 hash. The token itself exists only in
the user's cookie.

**`oauth_states`** holds the per-handshake secret (the PKCE verifier, or X's
request-token secret) and the return path for one handshake.
Rows are consumed once and deleted.

**`wallets.key_envelope`** is a JSONB AEAD envelope. There is no column anywhere
in this schema that can hold a private key, a mnemonic or a seed phrase, which
makes storing one a schema change rather than an accident.

**`shielded_notes.note_envelope`** is ciphertext addressed to the owner's viewing
key. `commitment` is unique per chain, so the same note cannot be recorded twice.
`nullifier_hash` is only ever written after a spend. `origin` records how the
note arrived -- `deposit` (the owner's own funds), `payment` (settled through a
payment link) or `transfer` (a shielded transfer from another account) -- and
`004_note_transfer_origin.sql` widened the check constraint when the third
became possible. A row here is a *delivery address*, not a claim that funds
exist: spendability is derived from the pool's own events and the chain's
nullifier set, so a row whose commitment never reached the chain is inert.

**`payments`** is the record of an attempt, not a claim of settlement. `privacy`
is `public` or `private` and is set from the actual flow, and `status` only
becomes `confirmed` when a receipt exists. `idempotency_key` is unique, so a
retried submission returns the original row.

**`rate_limits`** is a fixed-window counter shared by every instance of the app.
It is a brake, not a defence in depth, and it is documented as such.

**`audit_events`** records security-relevant operations such as wallet creation
and session creation. It holds no secrets.

## What is deliberately absent

- No plaintext keys, mnemonics, seed phrases or note secrets.
- No provider access tokens. They are used for one userinfo request and dropped.
- No OAuth client secrets. Those are environment variables.
- No passwords. There is no password column because there is no password flow.

## Access control

Every query in `app/api/` is scoped by the session's user id in the `WHERE`
clause. No route accepts a user id from the client. Filtering is never done in
the browser: a query that would return another account's rows is a bug in the
SQL, and it is written so that it cannot return them in the first place.

## Backups and recovery

Neon provides point-in-time restore on the project. Two consequences are worth
stating plainly:

- Restoring an older snapshot can resurrect a spend record. The chain remains the
  authority: a nullifier that is spent on chain is spent, whatever a restored
  payments table says.
- A restored `wallets` row is only useful if the user still has the passphrase.
  The database is not, and cannot be, a recovery mechanism for a wallet.
