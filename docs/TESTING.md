# Testing

## Running everything

```bash
npm run typecheck        # tsc --noEmit
npm run lint             # next lint
npm run test:unit        # protocol: Merkle tree and note format
npm run test:contracts   # Foundry: pool, tree, and a real Groth16 proof
npm run build            # production build
npm run chain:check      # live network assertions against Elysium testnet
npm run chain:verify     # every recorded contract address, read back over RPC
npm run chain:fork-test  # the deployed pool, on a fork, with a real proof
npm run e2e:shielded     # a whole private payment, sender to recipient, on testnet
```

Four checks need a running server and a real database, and all of them delete the
fixtures they create:

```bash
APP_URL=http://localhost:3200 npm run username:check   # registration, end to end
APP_URL=http://localhost:3200 npm run privacy:check    # the two payment paths
APP_URL=http://localhost:3200 npm run nav:check        # the nav drawer and signed-in routing
APP_URL=http://localhost:3200 NEXT_PUBLIC_ZK_PATH=$PWD/public/zk npm run e2e:shielded
```

`privacy:check` is the guard on the private/public split: a private payment is
opened without a destination address being handed to the payer, an address
cannot be smuggled into the private path, a private link cannot be settled as a
public transfer, a refused attempt does not spend the link's use, a private
payment cannot be recorded without the transaction that settled it, and an
external transfer still opens.

`e2e:shielded` is the one that answers the question the others cannot: does a
private payment actually work? It drives `src/lib/client/shielded.ts` -- the same
module the browser uses -- against the deployed pool. It creates two identities
with viewing keys, funds them from the deployment wallet, deposits a note, sends
a proof-verified shielded transfer to the recipient's *username*, has the
recipient decrypt the note the server only ever held as ciphertext, and withdraws
it to an external address. Seventeen checks, each read back from the chain. It
needs `NEXT_PUBLIC_ZK_PATH` because snarkjs resolves the proving artifacts itself
and, outside a browser, resolves them on disk.

It also needs the deployment wallet to hold enough testnet HYPE to bankroll the
two throwaway wallets it creates; it says so plainly and stops before spending
anything if it does not. Whatever those wallets have left goes back to the
deployment wallet on the way out, including after a failure, and the return is
itself an asserted check -- those mnemonics are generated per run and are gone
once the process exits, so a sweep that fails is money burned. Only the gas
reserve the sweep transaction needs stays behind, about 0.0000055 HYPE per
wallet. The faucet
has no API, so topping the wallet up is a manual visit to
https://elysium.kinetiq.xyz/testnet-faucet.

The two committed fixtures `tests/fixtures/transfer-*.json` are generated by the
same modules and are verified by the Foundry suite, so the circuit and the
contract are checked against each other without the network.

`nav:check` drives a real Chrome and measures the drawer at desktop, tablet and
phone widths. It exists because the drawer was once broken in a way no other
check could see: `.topbar` carries a `backdrop-filter`, which makes it the
containing block for `position: fixed` descendants, so the drawer and its scrim
were sized to the 60px header instead of the viewport. The menu opened,
reported `aria-expanded="true"` and rendered its items -- inside a sliver. It
skips itself when no Chrome or no server is available.

The same browser session then checks where the session sends people. Signed in,
the header's brand link points at `/dashboard`, following it lands there from
another page, the landing page redirects to `/dashboard`, and the public pages
that stay useful while signed in (`how-it-works`, `security`, `faq`, `terms`)
still answer 200 rather than being swallowed by the guard. Signing out is done
through the real route, and an app page is fetched afterwards to show the
session row is revoked rather than only the cookie cleared. Finally the
signed-out visitor keeps `/` with a brand link that points back at it.

The unit-test runner uses `node --import tsx --test --test-isolation=none`
rather than the `tsx` CLI, because the CLI's IPC socket is not permitted in a
restricted sandbox. Same tests, fewer moving parts.

## What is actually covered

### Protocol, `tests/unit/`

18 tests. Zero hashes are the Poseidon fixed point; an empty tree has the all-zero
root; insertion changes the root and preserves order; every leaf's proof
recomputes the root; a proof for one leaf does not verify another; a tree rebuilt
from the leaf list (which is what the indexer does) produces an identical root;
capacity is enforced; out-of-range proofs are rejected rather than silently
wrong. On notes: commitment and nullifier hash are derived rather than stored;
secrets never repeat; the amount comes from the denomination and not from user
input; unknown denominations are refused; encode/decode round-trips for every
denomination, including the dotted ids -- a note format split into a fixed number
of fields made every fractional note decode as malformed, which made funded notes
unspendable, so each size is round-tripped explicitly; malformed notes are
rejected instead of half-parsed; a tampered note fails its commitment comparison.

### Input parsing, `tests/unit/`

17 tests over the two pieces that decide what a payment is allowed to be.
`amount.ts` refuses zero, negative, malformed and over-precise values rather
than rounding them, converts decimal strings to wei without touching a float,
and round-trips; `address.ts` rejects anything that is not 40 hex characters,
catches a bad EIP-55 checksum, and refuses the zero address and the sender's
own address.

### Contracts, `contracts/test/`

40 tests, all passing. The three that matter most:

- `test_withdraw_accepts_a_real_proof` generates a Groth16 proof from the compiled
  circuit and has the **deployed verifier contract verify it on the EVM**. This is
  not a mock. The same code path runs on chain.
- `test_transfer_spends_a_note_and_mints_another` does the same for
  `transfer.circom`, which is the circuit a private payment actually uses, and
  `test_a_transferred_note_can_be_withdrawn` follows the note it mints all the way
  back out through a second proof.
- `test_empty_root_matches_typescript_implementation` pins the Solidity tree
  against the TypeScript tree, which is how the client and contract are kept from
  drifting.

Also covered: a replayed nullifier is rejected; a redirected recipient is
rejected; a tampered fee is rejected; a swapped proof point is rejected; an
unknown root is rejected; a stale root is rejected; a fee above the denomination
is rejected; a fee requires a relayer; fees split correctly to the relayer; wrong
deposit amounts and unknown denominations are rejected; direct transfers to the
pool are rejected; pausing blocks both directions; the owner cannot move pool
funds; the pool never owes more than it holds; a third party can submit a
transfer they did not author without being able to redirect it; and a nullifier
cannot be spent once as a withdrawal and once as a transfer.

### Fixtures

`tests/fixtures/withdraw-*.json` hold real proofs for a single-leaf tree, a
four-leaf tree, and a withdrawal with a relayer fee. `tests/fixtures/transfer-*.json`
hold a real transfer proof and a transfer followed by a withdrawal of the note it
created. All of them are used by the Foundry tests and are regenerated with
`npm run zk:prove-fixtures`.

## What is not covered, and why that matters

**The private-payment surface has no browser-driven test.** `npm run e2e:shielded`
drives the real client module, the real API routes and the real contracts against
Elysium testnet, and it is the check that a private payment works. What it does
*not* do is click the buttons: the deposit panel, the Send form's private mode
and the checkout panel are rendered and reviewed, not driven by a browser, and no
automated test covers them. `nav:check` is the only check that drives a browser
at all.

`npm run chain:verify` re-reads every recorded address over RPC, and
`npm run chain:fork-test` runs the deployed pool on a fork with a real Groth16
proof: a deposit and withdrawal settle, and a reused nullifier, tampered public
signals, an unknown root, a wrong deposit amount and an unknown denomination are
all refused.

**The OAuth flow has no automated test.** It needs registered redirect URIs and a
provider account. `src/lib/auth/oauth.ts` is written so the parts that can be
tested independently (state generation, PCKE pair integrity, the token-exchange
request shape) are separable, but the end-to-end flow is manual and is listed as
such rather than faked.

The failure paths that were exercised by hand while building: a mismatched
`state`; an expired handshake; a provider returning no code; a callback for an
unknown provider; a duplicate identity signing in twice; and a signed-out session
hitting a protected route.

**The interface was verified in a real browser**, not just inspected. Every route
was rendered at 1440px and at 390px with a seeded session, which is how several
defects were found and fixed: circle icons collapsing into lenses at small sizes,
three stacked stat cards eating half a phone screen, a sticky bottom navigation
overlapping page content, a fee estimate reporting "unavailable" for an unfunded
wallet, and a "Accepting private payments" badge being shown while the pool had no
deployment.

**Nothing has been audited.** Passing tests are not an audit, and this document
does not use the word to mean one.
